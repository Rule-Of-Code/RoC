# 7.8.1 → 7.9.1: the hook modes that narrowed the law set

This page keeps a piece of history that predates the public repository, so that a
claim made in public can be checked in public: in 7.8.1 the hook modes

frontend consumer's audit went from 122 laws to 27 — and 7.9.1 fixed it.

## CHANGELOG entries (verbatim)

## [7.9.1] - 2026-07-13

### 🔴 Fixed — hook modes silently collapsed the law set to the Pareto subset (P0)

Fixing a banner lie in 7.8.1 I wrote `paretoMode = finalMode !== 'full'`. There are
**four** modes, not two. So `--mode=pre-commit` and `--mode=pre-push` — the modes
that run on every commit and every push — fell through to the Pareto subset and
**silently dropped most of the law set**: a frontend consumer saw 122 laws collapse to 27, a backend consumer saw
100 collapse to 13. A consumer with an Audit Liveness floor was blocked from
pushing; a consumer **without** a floor lost ~78% of its gate and was told nothing.
This is exactly the failure this project exists to prevent: a gate that is quietly
disarmed is more dangerous than a gate that is missing.

Mode semantics are now explicit and separated:

- `fast` / `full` decide **which laws run** (Pareto subset vs the full set).
- `pre-commit` / `pre-push` decide **which files** are examined (`--staged`) and
  **never narrow the law set**. Hook modes inherit law scope from your config.

Unknown or mis-cased `--mode` values fail **open to the full set**, never to a subset.

- `paretoModeForCliMode()` is exported and unit-tested per mode.
- The test that should have caught this **asserted the defect** ("should display
  pareto header for any non-full mode"). It has been rewritten to assert the
  contract; the mode matrix is now covered at CLI level.

### 🟡 Fixed — a passing Pareto run no longer prints a compliance verdict

A run that deliberately executes a subset now prints `⚠️ PARTIAL SCAN PASSED —
N of M applicable laws (Pareto subset)`, not `COMPLIANCE`. The laws that did not
run cannot have passed, so we no longer say they did. The banner is derived from
the set that actually executed, so it can no longer disagree with reality.

### 🧰 Fixed — we were shipping (and running) the disarmed gate

`ruleofcode install-hooks` generated a lint-staged entry calling
`--mode=fast --staged`, i.e. we installed the Pareto subset as the commit gate in
**every** consumer repo. It now generates `--mode=pre-commit --staged`.

Our own `package.json` had the same line: RoC had been committing through the very
gate it exists to prevent. Fixed. The tool must catch its own author first (QA).

### 🐍 Fixed — Dependency Security Scanning was Node-blind on Python

A pure Python project (`uv.lock`, `pip-audit` in pre-commit and CI, bandit
alongside) failed with **four foreign demands** — "Missing lock file
(package-lock.json, yarn.lock…)" and "package.json not found" ×3 — while its
dependencies were, in fact, locked and scanned. Python consumers would have been
forced into a waiver, and forced waivers are what later hide real debt.

This is **not** an exemption: it is the same law, asked in the project's own
language. A locked graph plus a scanner in the gate is what the law *means*;
`uv.lock` / `poetry.lock` / `Pipfile.lock` / `pdm.lock` and `pip-audit` / `safety`
are how Python *says* it. A Python project with neither still fails.

### 🐛 Fixed — subscription-cleanup false positives (frontend consumer report)

Three laws flagged correct code: they matched text inside **comments**, and they
did not recognise modern Angular cleanup (`takeUntilDestroyed`, `DestroyRef`,
`toSignal`) as cleanup at all. Comments are now stripped before matching, and the
modern idioms count as what they are.

### 🔍 Fixed — Dependency Vulnerability Analyzer reported a vulnerability it never found

The checker incremented `mediumSeverity` when it found no security **config file**,
and then reported "1 medium vulnerability" — a finding about a missing file dressed
up as a finding about your dependencies. RoC contradicted `npm audit` (which said
0) and was wrong. It now reports what a scanner actually found, and separately
whether a scanner is present in the gate.

### 🧾 Fixed — `private: true` packages no longer demanded a license

Internal packages that are never published were told to add a LICENSE file and
were flagged UNLICENSED. `private: true` is the declaration that the concern does
not apply.

## [7.8.1] - 2026-07-12

### 🔴 Fixed (P0) — the meta-gates could disable themselves

Reported by QA against v7.8.0. **Audit Liveness (226)** and **Config Integrity
(227)** were ordinary selectable laws — so the very config mistake they exist
to catch also removed them. A `laws.enabled` allowlist of one law with
`minLawsChecked: 90` ran **1 law, skipped both guards, and printed PASSED with
exit 0**: literally the v7.5.1 incident class, inside the guard against it.

- Both guards are now **always enabled** — no `paretoMode`, no `laws.enabled`
  allowlist and no `notApplicable` waiver can drop them. *A meta-gate a config
  can disable is not a gate.*
- The liveness floor is enforced **in the engine**, like the zero-laws refusal —
  not only by law 226, because the config that shrinks the selection could have
  dropped that law too.
- Guards do **not** count as evidence: liveness is measured in *substantive*
  laws. (Without this, making them always-on would have quietly broken the
  zero-laws refusal — the suite caught exactly that.)
- Law 226's default 25% floor no longer punishes a **deliberate** narrowing
  (explicit allowlist / paretoMode); there the project declares its own floor
  via `laws.minLawsChecked`, which the engine enforces hard.

| scenario | laws | guards | exit |
|---|---|---|---|
| full set | 100 | ✅ | 1 |
| `paretoMode` + floor 90 | — | REFUSED | 1 |
| allowlist(1) + floor 90 | — | REFUSED | 1 *(was PASSED, exit 0)* |
| allowlist(1), no floor | 3 | ✅ | 0 *(deliberate, guarded)* |
| empty allowlist | — | REFUSED | 1 *(zero-refusal intact)* |

### 🟠 Fixed — a law name RoC prints must gate as a config key

Sixteen checkers reported **local** names (e.g. `semver-compliance` for
"Semantic Versioning Standards"), which the identity contract — built from the
registry name — rejected as unknown laws. Nine of them are Angular laws, so a
frontend keying `laws.severity` by what the audit printed would have gated
nothing. The engine now reports the **canonical slug** for every law, and a
per-law test asserts all 173 reported names resolve as config keys.

### 🔵 Fixed — two smaller lies

- `audit --mode=fast` on a `paretoMode: false` config printed
  "PARETO OPTIMIZATION ACTIVATED" and then ran the **full** set. An explicit
  `--mode` now drives law selection too: the banner and the executed set agree.
- **Test Data Management** returned `passed: false` with **zero violations** and
  a "✅ Excellent test data practices" message — two score deductions pushed
  only suggestions. What costs you the gate must be printable: they are
  violations now, and violations are the verdict.

**What consumers must do:** nothing. If you deliberately run a narrow law set
(`laws.enabled` / `paretoMode`), declare `laws.minLawsChecked` — the engine
enforces it as a hard refusal, and the two guards always run regardless.
